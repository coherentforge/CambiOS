# CambiOS Implementation Status

> **Living doc.** Single source of truth for "what is currently built." Auto-refreshed as feature work lands (see [CLAUDE.md § Post-Change Review Protocol Step 8](CLAUDE.md#post-change-review-protocol)). Intent lives in [CambiOS.md](docs/CambiOS.md) and the design docs; this file is for *current state*.
>
> "Is X done yet?" — read here. "Should X be done a certain way?" — read the linked design doc.

## At a glance

- **Tri-arch first-class**: clean release build on `x86_64`, `aarch64`, `riscv64gc` (`make check-all` is the permanent gate); all three boot in QEMU to the `cambios>` shell under init-supervised boot (ADR-018 step 9 — the manifest is the only thing that starts anything: x86_64/aarch64 15-service wave + 5 on-demand apps, riscv64 11-service wave).
- **Host unit tests passing** on `x86_64-apple-darwin`. Run `make stats` for the current count — numbers live in code, not prose.
- **Security model live end-to-end**: cryptographic identity, signed-ELF verification, capability-gated IPC, content-addressed ObjectStore, audit ring, kernel identity gate, userspace `recv_verified`.
- **GUI stack live on x86_64 + aarch64**: scanout-virtio-gpu drives QEMU virtio-gpu-pci; compositor composites; virtio-input forwards HID keyboard/pointer events into the focused window; first-party app `pong` (continuous-motion 1-player vs AI) runs as the default GUI boot module on x86_64, and `worm` renders on aarch64 via `make run-aarch64-gui` now that the kernel has an ECAM-based PCI enumerator. `tree` (Minesweeper) stays buildable for regression.
- **Persistent storage live**: virtio-blk + disk-backed ObjectStore + `arcobj` shell CLI; objects survive reboot.
- **Bare metal**: USB boot tooling complete, untested on hardware.
- **Formal verification**: Kani proofs live on BuddyAllocator + ELF parser + FrameAllocator + CapabilityManager + UserSlice + DTB parser (1 + 7 + 11 + 12 + 12 + 5 = 48 harnesses across 6 proof crates; proof authoring fixed 6 overflow sites in `src/loader/elf.rs`, 2 in `src/memory/frame_allocator.rs`, and 2 in `src/boot/riscv.rs`). [verification/CLAIMS.md](verification/CLAIMS.md) tracks the gap between proven and aspirational claims.

- **2026-09-14** — **riscv64 boot rot root-caused and fixed; riscv64 boots supervised (11/0/0).** Not one bug but a class: large kernel structs materialized on the boot stack. `Box::new(ClusterManager::new())` (74,888 B), `Box::new(ChannelManager::new())` (58,376 B) and `let info = BootInfo::empty()` (17,320 B) each build the whole struct on the caller's stack before it reaches the heap/static; the riscv64 boot stack was 16 KiB, and `llvm-nm` shows `POLICY_ROUTER`, `TASK_CPU_MAP` and `AUDIT_RING` linked immediately below it — so write-once statics read back as garbage, with the victim shifting as layout shifted (the policy-router panic at 16 KiB; at a 64 KiB probe stack only `AUDIT_RING` was hit → `Some(zeroed ring)`, physical base 0, audit-tail's mapped ring pointing at nothing → the 'load access fault'). x86_64/aarch64 never noticed on Limine's 256 KiB stack. Fixes: in-place `new_boxed` for ClusterManager + ChannelManager (field-wise writes, Convention 7-safe, `IpcManager` was already the reference); `BootInfo::init_empty_at` + `boot::begin_install()` builder so both boot adapters populate the static in place (`empty()`/`install()` are test-only now; `empty_literal` keeps the exhaustive field list compile-checked); riscv64 `BOOT_STACK_SIZE` 16 → 256 KiB (Limine parity; ASSUMPTIONS rows for BSP + AP stacks); `audit_init()` added to the riscv64 sequence (it was simply missing — audit-tail's attach had returned -1 on every riscv64 boot); typed `BootError::BootInfoAlreadyClaimed` for the Limine adapter's refusal path. Then the deferred commit-D staging goes back in: manifest.bin + init in the riscv64 initrd. Convention 4 rewritten in CLAUDE.md (`Box::new(T::new())` is not the pattern) + a new Common Failure Signature. Verified: riscv64 legacy boot to shell (11.0s) then supervised `wave settled: 11 ready, 0 spawn-failed, 0 dep-failed` (8.9s); aarch64 supervised 15/0/0 through the new builder (19.7s); x86_64 wave settled; 926 host tests; tri-arch build + clippy clean.
- **2026-09-14** — **ADR-018 step 8 commit D: aarch64 boots supervised; per-arch manifests; riscv64 staging deferred on discovered boot rot.** manifest.toml gains per-service `arch` tags (the four GUI-stack services are x86_64+aarch64) and build-manifest a `--arch` filter with a dependency-closure check — each deployment's manifest matches its reality (riscv64 = 11 services, no phantom spawn failures). aarch64 stages manifest.bin + init.elf in the FAT image + limine-aarch64.conf and boots fully supervised: `wave settled: 15 ready, 0 spawn-failed, 0 dep-failed` (GUI-mode; serial-only mode stalls at the compositor↔scanout handshake exactly as the legacy chain did — both sides defer the timeout to the other, pre-existing, see the code comments). ## Known issues (active)

- **riscv64 serial input reaches the shell for one byte only (observed 2026-09-22).** Typing `faultme` at the riscv64 `cambios>` prompt echoes `f`; every later byte is printed by the kernel's `[R-3 RX] 0xNN` UART diagnostic instead of being delivered to the shell's console read. x86_64 and aarch64 deliver the whole line. Pre-existing (the R-3 RX route predates ADR-018); interactive riscv64 proofs must spawn from the manifest wave until fixed. Revisit when: the next riscv64 console-path change (PLIC/UART RX → `SYS_CONSOLE_READ` waiter) is touched.

- **QEMU cocoa display can go non-responsive during GUI gameplay while the guest stays healthy (observed 2026-09-14, `make run-gui` + `play tree` + mouse clicks).** Discriminator: check the serial console — if audit lines are still flowing (input driver, compositor, scanout, game all emitting `ipc.send`), the guest and QEMU's emulation are fine and only the host cocoa UI is stuck; quit and relaunch. The same click session replayed headlessly (`-display none` + monitor-injected clicks) survives, including an unrequested edge-grab resize tearing down and rebuilding the game's channel mid-play (generation-carrying recycle held). Two deferred GUI follow-ups feed this: cursor-not-functional (guest pointer position drifts from the host cursor under cocoa's relative-mouse stream, so clicks land off-target — how a square-click becomes an edge-grab) and games' missing resize-protocol adoption (C12e stubs). Revisit when: GUI work resumes (the 2026-05-10 deferred pair) OR it reproduces under a non-cocoa display backend.
- **FDE fresh-wrap install flake (transient, 1-in-5 observed 2026-08-23).** Signature: `[FDE-MOUNT] FAIL at install_master_key: -3` (OutOfMemory) during `make run-quiet-dev-piv`, from `DiskObjectStore::format_with_auto_geometry` failing once on the fresh-wrap path; the identical tree then unlocked clean 3/3 (`substrate now mounted on XTS-AES-256`). Not the UnlockVolume gate (a gate rejection reads -2), and a pre-change baseline was also single-sample green, so attribution to any specific commit is unsupported — reads as a transient in the format path's virtio-blk IPC dance. The handler now prints the underlying format error at the failure site (added 2026-08-23), so the next occurrence names its cause instead of hiding behind the blanket OutOfMemory. Also note: the dev-piv smoke's default sentinel (shell prompt) can fire before fde-mount's outcome line — proof runs should use `SUCCESS="master key installed"`. Revisit when: it recurs with the new diagnostic line visible.
- **Boot-stall flake — root cause found and fixed 2026-09-14 (lost IPC wake-up); watching for recurrence.** The 2026-07-10 terminal-window second-layer stall and the 2026-09-14 supervised-boot-wave stall (init slept through fs-service's ready ping; wave froze after `[FS] seeded demo objects`) were the same mechanism: `handle_write`'s post-enqueue wake scanned only the SENDER'S local scheduler, so a receiver blocked on the other CPU was never woken — placement-dependent, hence the flake shape and the binary-layout sensitivity (layout perturbs task/CPU timing, not any queue). Two fixes landed: `wake_message_waiters_all_cpus` (plain-lock scan of every online CPU's scheduler; also replaces the try_lock loops at the policy + virtio-blk wake sites, which could silently skip a contended scheduler) and a lost-wakeup guard in `handle_recv_msg` (queue re-check held atomic with `block_task` under SCHEDULER(1) → IPC(3), closing the check-then-block gap). Proven: 6/6 supervised boots to `wave settled: 15 ready` + dev-piv unlock, where the wave rolls 15 sleep/wake round-trips per boot. Revisit when: any silent one-task-sleeps stall recurs — the Common Failure Signatures entry now names the diagnosis path; the GUI queue-fill architectural pass keeps its own second-pointer-app trigger (it was the suspected mechanism here and is now exonerated for this signature).

- **AArch64 SMP timer on AP**: PPI 30 not firing on second CPU under QEMU `virt`. Single-CPU works fully. Likely QEMU config or missing GIC redistributor step on the AP path. Investigation pending.
- **AArch64 device IRQ routing**: GIC `enable_spi` / `set_spi_trigger` exist but are not called from the boot path or `handle_wait_irq`. No device IRQs on aarch64 today. **Revisit when:** first aarch64 path needs device IRQs (likely a polling→IRQ-driven transition in virtio-blk, or resolution of the AP-timer gap enabling PL011 RX to drive a consumer).
- **ELF loader overlapping-segment permissions**: If two PT_LOAD segments share a page with different permissions, the first segment's permissions win. Worked around in user-space linker scripts via `ALIGN(4096)` before `.data`.
- **Kernel stack not freed on process exit**: `handle_exit` now performs full lifecycle cleanup (Phase 3.2d.ii), but the 32 KiB kernel stack per task remains a bounded leak — can't free the stack you're running on. Requires scheduler-level deferred-dealloc. Bounded by `num_slots × 32 KiB` (~6.4 MiB worst case).
- **Clippy warnings** (~125): ~67 `multiple_unsafe_ops_per_block` in arch code, ~25 missing `// SAFETY:`, ~12 `static_mut_refs` (Rust 2024 migration — IDT/GDT/TSS patterns need `UnsafeCell` or `addr_of!`), ~20 `new_without_default`. Dedicated pass scheduled before `static_mut` deprecation becomes a hard error.
- **Pre-existing driver warnings** in `user/i219-net/`: `dead_code` / `unused_imports` from scaffolded state. Not correctness issues; clean up on next real-hardware bring-up.
- **Virtio-net TX on QEMU TCG**: QEMU defers virtio TX to its event loop, which runs during guest `hlt`. The UDP stack's ARP retry/timeout logic doesn't yet exploit this fully.
